CROSS-CUTTING

Four rules the whole file obeys

Every function is a variation on the same commitments. Once you see them, the file stops being ten separate problems.

Rule 01

Augmentation can only reach train

Both loader builders map splits to transforms in one dictionary, with validation and test hard-wired to evaluation_transform(). No argument can put a random transform on an evaluation split.

Rule 02

Load strictly, then replace

The ImageNet state dictionary is loaded into the unmodified 1000-class model with strict=True, and only then is the last head layer swapped. Every pretrained tensor is checked by key and shape; none can be silently left random.

Rule 03

Mode and gradients are always set explicitly

Training calls .train(). Everything that measures — evaluate_model, predict, extract_embeddings — is decorated @torch.no_grad() and calls .eval(). No function inherits a mode from whatever ran before it.

Rule 04

Order is part of the contract

Only training shuffles, from a private seeded generator. Evaluation arrays come back in loader order, so labels, predictions, probabilities, embeddings, and predictions.csv rows all line up by index.

01

A data pipeline that only randomizes training

64×64 arrays in, 224×224 ImageNet-normalized tensors out — with every source of randomness either seeded or absent.

student_code.py:20–59 · constants, evaluation_transform, training_transform

IMAGENET_MEAN = (0.485, 0.456, 0.406)
IMAGENET_STD = (0.229, 0.224, 0.225)
IMAGE_SIZE = 224

def evaluation_transform(image_size=IMAGE_SIZE):
    return transforms.Compose([transforms.Resize((image_size, image_size))]
                              + _normalization())

def training_transform(augmentation, image_size=IMAGE_SIZE):
    if augmentation == "none":
        return evaluation_transform(image_size)
    if augmentation == "moderate":
        steps = [Resize((s, s)), RandomHorizontalFlip(0.5),
                 RandomVerticalFlip(0.5),
                 ColorJitter(brightness=0.2, contrast=0.2)]
    else:   # strong
        steps = [RandomResizedCrop(s, scale=(0.6, 1.0), ratio=(0.8, 1.25)),
                 RandomHorizontalFlip(0.5), RandomVerticalFlip(0.5),
                 RandomRotation(30),
                 ColorJitter(0.4, 0.4, 0.4, hue=0.1), RandomGrayscale(0.1)]
    return transforms.Compose(steps + _normalization())

ToTensor moves the channel axis first and scales to [0, 1]; Normalize applies the ImageNet statistics, because those are what the pretrained filters were trained on. The notebook's printed range (−2.001, 2.64) is the result.

Every split is resized to 224, the scale the backbones learned at. none is the evaluation transform, so Experiment 3's baseline differs from evaluation in nothing.

moderate is label-preserving for all six classes — flips map stripes, checkers, circles, dots, and diagonals onto their own class. strong adds a ±30° rotation and random crops, which start to erode the orientation evidence the horizontal / vertical / diagonal classes are defined by.

Why validate first

The level is checked before anything is built, so "Strong" fails in microseconds rather than after a ten-epoch run — or, in build_external_dataloaders, before a 3.7 GB download.

A private generator per training loader makes the shuffle order a function of seed alone, independent of how much of the global RNG earlier cells used. The DataLoader also draws each epoch's worker seed from it, so augmentation draws inside workers are reproducible too; _worker_init extends that to NumPy and Python's random.

_drop_last drops a trailing batch only if it holds exactly one image — BatchNorm cannot compute a training-mode variance from one sample. 720 % 32 = 16, so it never fires on the bundled data; it exists for arbitrary Hugging Face split sizes.

ArrayImageDataset wraps each array as a PIL image on demand because torchvision transforms expect PIL input. It is public because the notebook reuses it for noisy test sets, corrupted labels, and rotated training data.

An offline pretrained model, and a precise idea of "the head"

Build bare, load strictly, replace one layer, and write down exactly which parameters that layer owns.

student_code.py:135–168 · build_model, freeze_backbone, unfreeze_all

model = getattr(torchvision.models, architecture)(weights=None)
state_dict = torch.load(Path(weights_path), map_location="cpu",
                        weights_only=True)
model.load_state_dict(state_dict)                 # strict=True

head_index = len(model.classifier) - 1
old_head = model.classifier[head_index]
model.classifier[head_index] = nn.Linear(old_head.in_features,
                                         int(num_classes))
model.a3_head_parameters = tuple(
    f"classifier.{head_index}.{name}"
    for name, _ in model.classifier[head_index].named_parameters())

def freeze_backbone(model):
    head = set(getattr(model, "a3_head_parameters", ()) or ())
    for name, parameter in model.named_parameters():
        parameter.requires_grad = (name in head) if head \
                                  else ("classifier" in name)
    return model

weights=None builds the architecture with no download. weights_only=True restricts torch.load's pickle to tensors and plain containers, the safe setting for any file from elsewhere. strict=True means every key must match in both directions.

len(model.classifier) - 1 finds the last layer of either head — index 3 for MobileNet, 1 for EfficientNet — and in_features reads its width (1024 / 1280) instead of hard-coding it.

Why record exact parameter names

MobileNet's head starts with a pretrained Linear(576, 1024). "Everything with classifier in its name" would unfreeze its 590,848 weights too. The stored names keep exactly the replacement layer trainable: 6,150 numbers for MobileNet, 7,686 for EfficientNet. The substring rule is only a fallback for models not built here.

03

Training and measuring, kept apart

One function changes weights. Three functions only look — and each of them switches both autograd and layer behaviour off.

student_code.py:171–190 · train_one_epoch

model.to(device).train()
for images, labels in loader:
    images = images.to(device, non_blocking=True)
    labels = labels.to(device, non_blocking=True)
    optimizer.zero_grad(set_to_none=True)
    logits = model(images)
    loss = criterion(logits, labels)
    loss.backward()
    optimizer.step()
    count = labels.numel()
    total_loss += float(loss.detach()) * count
    total_correct += int((logits.detach().argmax(dim=1) == labels).sum())
    total_seen += count
return {"loss": total_loss / total_seen,
        "accuracy": total_correct / total_seen}

Zero → forward → loss → backward → step. set_to_none=True frees gradient tensors rather than zero-filling them, and leaves a frozen parameter's .grad as None.

The criterion returns a batch mean, so it is multiplied back by the batch size: the result is the true per-sample mean even when the last batch is short. .detach() keeps the running sum from holding every batch's autograd graph.

A running average, not a clean score

Training accuracy is accumulated while the weights change, with dropout on and augmentation applied. That is why the notebook often shows training accuracy below validation accuracy — a negative gap is expected, not a bug.

@torch.no_grad()
def predict(model, images, device):
    model.to(device).eval()
    logits = model(images.to(device))
    probabilities = torch.softmax(logits, dim=1)
    return {"predictions": logits.argmax(dim=1).cpu(),
            "probabilities": probabilities.cpu()}

@torch.no_grad() and .eval() are different switches. The first stops autograd from building a graph; the second turns dropout off and makes BatchNorm use its stored statistics. Evaluation needs both.

Softmax runs over dim=1, the class axis. Predictions come from the logits' argmax, which equals the probabilities' argmax because softmax preserves order.

evaluate_model returns NumPy arrays in loader order; predict returns CPU tensors for one batch. Whichever criterion is passed is used — the notebook always passes plain cross-entropy here, so label-smoothed runs are measured on the same scale.

04

One table, every metric — and what the network actually learned

Rows are true classes, columns are predictions. Precision reads a column, recall reads a row, and the embedding is whatever feeds the last layer.

student_code.py:257–291 · classification_metrics

count = len(class_names)
matrix = np.zeros((count, count), dtype=np.int64)
for true_label, predicted_label in zip(labels, predictions):
    matrix[true_label, predicted_label] += 1

true_positive   = np.diag(matrix).astype(np.float64)
predicted_total = matrix.sum(axis=0).astype(np.float64)   # columns
actual_total    = matrix.sum(axis=1).astype(np.float64)   # rows
with np.errstate(divide="ignore", invalid="ignore"):
    precision = np.where(predicted_total > 0, true_positive / predicted_total, 0.0)
    recall    = np.where(actual_total > 0, true_positive / actual_total, 0.0)
    f1 = np.where(precision + recall > 0,
                  2 * precision * recall / (precision + recall), 0.0)
return {..., "per_class_accuracy": recall.copy(),
        "support": actual_total.astype(np.int64),
        "macro_f1": float(f1.mean())}

The matrix is sized by class_names, not by the labels present, so a class that is never predicted still has a column — Experiment 8's dermatofibroma (precision 0, recall 0) needs that.

Undefined ratios become 0, not NaN, so macro-F1 always computes. np.where evaluates both branches; errstate silences the warning from the discarded one.

Per-class accuracy as the task defines it, TP / (TP + FN), is recall. It is returned as a copy, so the two arrays cannot alias. macro_f1 weights every class equally — which is why Experiment 8 shows 0.795 accuracy beside 0.479 macro-F1.

student_code.py:231–254 · extract_embeddings

@torch.no_grad()
def extract_embeddings(model, loader, device):
    model.to(device).eval()
    captured = []

    def hook(_module, inputs, _output):
        captured.append(inputs[0].detach()
                        .flatten(start_dim=1).cpu().numpy())

    handle = model.classifier[-1].register_forward_hook(hook)
    try:
        for images, labels in loader:
            model(images.to(device))
            all_labels.append(np.asarray(labels).reshape(-1))
    finally:
        handle.remove()

The embedding is never returned by forward, so a forward hook on the final layer captures its input — exactly the vector the head classifies, for both architectures, without re-implementing either forward pass. 1024-d for MobileNet, 1280-d for EfficientNet.

flatten(start_dim=1) guarantees (batch, features). Copying to the CPU inside the hook keeps GPU memory flat.

Why finally

A hook stays attached until removed. Left behind, it would fire on every later forward pass — training, evaluation, the next extraction — appending to a list nobody reads. finally removes it even if a batch raises.

07

Sharp edges

Nothing here fails the public tests. These are places where the code makes a choice worth defending, or where its evidence in the notebook reads wrong.

Verifying a load or a mode needs the right momentcells a3bc3d4b, bcda558b

Two notebook checks first printed False for correct functions. Task 2 compared the backbone with the weight file after a training-mode forward pass, which had already updated 102 BatchNorm buffers; Task 3 read torch.is_grad_enabled() after evaluate_model had returned and restored gradients. Both cells now check at the right moment — before the forward pass, and from a hook inside the evaluation call — and print True.

Frozen is not the same as unchangingtrain_one_epoch:174

model.train() applies to the frozen backbone too: its BatchNorm running statistics adapt to the new data and its dropout is active. "Frozen" fixes the learnable weights, not the buffers. A strict linear probe would put the backbone in eval mode during training.

Negative labels index silentlyclassification_metrics:275–276

A label of -1 would increment the last row instead of raising, because NumPy accepts negative indices. Labels above K−1 do raise. Every caller here produces valid labels, but a range check would make the failure loud.

One GPU sync per batchtrain_one_epoch:185–186

float(loss) and int(...sum()) copy to the host every step, which forces the GPU to finish the step first. On these models it is invisible; on a large model, accumulating on the device and converting once per epoch would remove the stall.

Seeded is not the same as deterministic on a GPUa3_tools.seed_everything

Every random generator is seeded, but cuDNN's convolution backward kernels may still sum in a different order from run to run. Two runs of the notebook matched bit-for-bit on every frozen run and differed on full fine-tuning: Experiment 9's fine-tuned test accuracy was 0.9750 in one run and 0.9674 in the next. torch.backends.cudnn.deterministic = True plus torch.use_deterministic_algorithms(True) would remove that, usually at some speed cost.

A loaders object keeps its shuffle statebuild_external_dataloaders:436

Each training loader owns one generator that advances every epoch. Reusing a loader for a second run continues the sequence rather than restarting it — Experiment 9's frozen probe trains on a different batch order from the fine-tuned run it is compared with. Building fresh loaders per run, as run_training does for the bundled data, restarts it.
